# Tasker — правила работы в этом репозитории (вариант Б: ядро на Go)

**Начни с `docs/AGENTS.md`** — что в проекте уже есть, какие слои, методы и решения. Дальше по надобности: `docs/SPEC.md` (что строим), `docs/ROADMAP.md` (в каком порядке), `docs/MCP.md` (контракт агента), `docs/VARIANT.md` (почему этот стек и в чём его слабости), `docs/DESKTOP.md` (справка по устройству десктопных приложений, не требования).

Папки `oak-go/` и `oak-ts/` — исходный материал, из которого вырос проект: две редакции спеки под разные стеки и пробы фазы 0. Читать оттуда можно, писать туда не нужно; живые документы лежат в корневом `docs/`.

Стек: **Go 1.25+ · Wails v3 (бета) · modernc.org/sqlite · React 19 + CodeMirror 6 в WKWebView**.

---

## Инварианты — нарушать нельзя

1. **Файлы — источник правды.** SQLite-индекс производный. Сначала пишем файл, потом обновляем индекс. Индекс разошёлся с диском — правильный ответ «перестроить индекс», а не «поправить файл под индекс».
2. **Ничего не теряем.** Запись `.md` только атомарная: временный файл рядом → `fsync` → `rename`. Неизвестные поля frontmatter сохраняются. Никогда не вызывать `git reset --hard`, `git clean`, `git checkout -- .`, force-push в vault пользователя.
3. **Вся логика — в Go.** Фронтенд не парсит frontmatter, не строит запросы, не ходит в файловую систему, не знает о SQLite. Он вызывает биндинги и рисует. Если понадобилось «просто по-быстрому распарсить на стороне JS» — это ошибка проектирования, метод добавляется в Go.
4. **`internal/vault`, `internal/index`, `internal/watcher`, `internal/gitstore`, `internal/notes` не импортируют Wails.** Они должны собираться и тестироваться обычным `go test`. Wails живёт только в `internal/app` и `cmd/tasker`.
5. **`frontend/bindings/` — сгенерированный код.** Руками не редактируется никогда. Изменения только через `wails3 generate bindings`.
6. **Никакой системы плагинов.** Приложение для одного человека, всё правится в исходнике. Не вводить абстракции «на будущее».
7. **Никакого AI-кода в приложении.** Ни SDK моделей, ни ключей, ни запросов. Интеллект приходит снаружи через `cmd/tasker-mcp`.
8. **Vim-режим — не опциональная фича.** Любой новый шоткат проверяется на конфликт с вимом.

## Go: стиль

- Ошибки оборачиваются с контекстом: `fmt.Errorf("read note %s: %w", path, err)`. Никаких голых `return err` там, где теряется путь или id.
- Свои типы ошибок для того, что вызывающий должен различать: `ErrNoteNotFound`, `ErrOutsideVault`, `ErrConflict`. Проверять через `errors.Is` / `errors.As`.
- `context.Context` первым параметром во всём, что ходит в базу или файловую систему.
- Конкурентность: **сервисы Wails — синглтоны, вызовы из вебвью приходят параллельно, никто их не сериализует.** Запись в SQLite — через одну горутину или мьютекс. Не полагаться на то, что «вызовы и так по одному».
- Никаких глобальных переменных и `init()` с побочными эффектами. Зависимости передаются в конструкторы.
- Экспортируется только то, что действительно нужно снаружи пакета.
- Комментарии объясняют **почему**, а не что.

## Go: зависимости

Список в SPEC §3. Новые пакеты — только с явного согласия. Особенно:

- **Не добавлять cgo-зависимости.** Весь смысл выбора `modernc.org/sqlite` в том, что сборка остаётся без cgo и universal binary собирается тривиально. Одна cgo-зависимость это ломает.
- Не тащить `gopkg.in/yaml.v3` — он не поддерживается с апреля 2025. YAML только через `goccy/go-yaml`.
- Не тащить `go-git/v6` — он полтора года в альфе. Только `v5`.
- Не тащить ORM. Здесь голый `database/sql` и запросы руками — их немного и они простые.

## Frontend: стиль

- TypeScript strict. `any` только с комментарием.
- Никаких UI-китов (MUI, Chakra, Ant), никакого CSS-in-JS, никакого state-менеджера кроме zustand — и тот минимально, состояние живёт в Go.
- Компоненты тупые: получили данные, отрисовали, вызвали биндинг. Бизнес-правил в компонентах нет.
- CSS — обычный, переменные из `theme/`.

## Тесты

- `internal/*` — `go test`, обязательно. Особенно: round-trip frontmatter (включая неизвестные поля, комментарии и порядок ключей), парсер языка запросов, разрешение коллизий имён файлов, инкрементальный скан, игнор собственных записей watcher'ом.
- Тесты пишутся до реализации там, где поведение легко описать таблицей — а здесь это почти всё.
- UI — минимально, только критические сценарии.
- Фаза не считается закрытой, пока не прогнан её сценарий приёмки из ROADMAP.

## Сборка и коммиты

- Сборка через Taskfile: `wails3 dev` для разработки, `wails3 task darwin:build:universal` для релиза.
- Версия Wails пинится точно. При апгрейде — прочитать changelog, перегенерировать биндинги, прогнать тесты.
- Коммиты в императиве, английский, без эмодзи. Один коммит — одно изменение.
- Не коммитить `.tasker/index.sqlite*`, `build/bin`, `frontend/dist`, `node_modules`.

## Как работать над задачей

1. Найди фазу в `docs/ROADMAP.md`. Задача не из текущей фазы — скажи об этом до того, как делать.
2. Прочитай раздел `docs/SPEC.md`. Спека противоречит просьбе — не додумывай, спроси.
3. Порядок: типы и сигнатуры в `internal/` → тесты → реализация → сервис Wails → UI.
4. Не расширяй объём. Увидел смежную проблему — скажи отдельно, не чини по дороге.
5. Закончил — назови, что именно проверить руками.

## Чего не делать

- Не рефакторить то, о чём не просили.
- Не добавлять фичи из «не входит в объём» (SPEC §9), даже если это пять строк.
- Не писать README и CHANGELOG без просьбы.
- Не заводить абстракции под один случай использования.
- Не глушить ошибки без логирования и без явного решения, что с ними делать.
- Не «чинить» гонку редактора и watcher добавлением задержек наугад. Механизм описан в SPEC §5.3, он один.
