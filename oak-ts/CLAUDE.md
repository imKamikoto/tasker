# Oak — правила работы в этом репозитории (вариант А: всё на TypeScript)

Читай вместе с `docs/VARIANT.md` (почему этот стек, в чём его слабости и кто пользователь — **начни с него**), `docs/SPEC.md` (что строим), `docs/ROADMAP.md` (в каком порядке) и `docs/MCP.md` (контракт агента).

Стек: **Electron · TypeScript · React 19 · CodeMirror 6 · better-sqlite3**.

---

## Инварианты — нарушать нельзя

1. **Файлы — источник правды.** SQLite-индекс производный. Любая операция сначала пишет файл, потом обновляет индекс. Если индекс разошёлся с диском — правильный ответ «перестроить индекс», а не «поправить файл под индекс».
2. **Ничего не теряем.** Запись `.md` только атомарная: временный файл рядом → `fsync` → `rename`. Неизвестные поля frontmatter сохраняются при перезаписи. Никогда не вызывать `git reset --hard`, `git clean`, `git checkout -- .` или force-push в vault пользователя.
3. **Вся работа с данными — в `packages/core`.** Ни рендерер, ни MCP-сервер не читают и не пишут файлы сами. Если понадобилась новая операция над данными — она добавляется в core с тестом, а не пишется на месте.
4. **Никакой системы плагинов.** Не вводить абстракции «на будущее»: реестры компонентов, зоны лейаута, хуки для расширений. Приложение для одного человека, всё правится прямо в коде.
5. **Никакого AI-кода в приложении.** Ни SDK, ни ключей, ни запросов к моделям. Интеллект приходит снаружи через MCP.
6. **Vim-режим — не опциональная фича.** Любой новый шоткат проверяется на конфликт с вимом.

## Структура

```
packages/
  core/     данные: vault, frontmatter, индекс, поиск, watcher, git. Без Electron, без React.
  app/      Electron main + preload + renderer (React, CM6)
  mcp/      MCP-сервер поверх core
theme/      CSS-переменные, дубовая палитра
docs/       SPEC.md, ROADMAP.md, MCP.md
```

`core` не импортирует ничего из `app` и `mcp`. Проверяется линтером.

## Стиль кода

- TypeScript strict. `any` — только с комментарием, объясняющим почему.
- Никаких классов ради классов; сервисы — фабричные функции, возвращающие объект с методами.
- Ошибки — свои типы (`VaultError`, `IndexError`) с полем `code`, а не голые строки.
- Асинхронность — `async/await`. `better-sqlite3` синхронный, это нормально, не оборачивать в промисы.
- Комментарии объясняют **почему**, а не что. Код, требующий комментария «что», переписывается.
- Русский в UI-строках, английский в коде и коммитах.

## Зависимости

Не добавлять новые пакеты без явного согласования. Список разрешённого в SPEC §3. Особенно: **никаких UI-китов** (MUI, Chakra, Ant), **никакого CSS-in-JS**, **никакого state-менеджера кроме zustand**.

## Тесты

- `packages/core` — юнит-тесты обязательны, vitest. Особенно: round-trip frontmatter, парсер языка запросов, разрешение коллизий имён файлов, инкрементальный скан.
- UI — playwright поверх Electron, только на критические сценарии: создать заметку, сменить статус, найти, перезапустить и убедиться, что всё на месте.
- Перед тем как считать фазу закрытой — прогнать `pnpm test` и сквозной сценарий приёмки из ROADMAP.

## Коммиты

- Осмысленные сообщения в императиве, английский, без эмодзи.
- Один коммит — одно изменение. Не смешивать рефакторинг с новой фичей.
- Не коммитить `.oak/index.sqlite*`.

## Как работать над задачей

1. Найди фазу в `ROADMAP.md`, к которой относится задача. Если задача не из текущей фазы — скажи об этом, прежде чем делать.
2. Прочитай соответствующий раздел `SPEC.md`. Если спека противоречит просьбе — не додумывай, спроси.
3. Начни с типов и сигнатур в `core`, потом тесты, потом реализация, потом UI.
4. Не расширяй объём. Увидел смежную проблему — скажи о ней отдельно, не чини по дороге.
5. Когда закончил — назови, что именно проверить руками.

## Чего не делать

- Не рефакторить то, о чём не просили.
- Не добавлять фичи из раздела «не входит в объём» (SPEC §9), даже если это пять строк.
- Не писать README, CHANGELOG и прочую обвязку без просьбы.
- Не заводить абстракции под один-единственный случай использования.
- Не глушить ошибки в `try/catch` без логирования и без явного решения, что с ними делать.
